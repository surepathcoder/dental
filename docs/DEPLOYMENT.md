# Deployment guide

Two deployables: the **Next.js frontend** (Vercel) and the **FastAPI backend + PostgreSQL**
(Render or Railway). They're connected by two environment variables: the frontend's `API_URL` and a shared
`ADMIN_API_KEY`.

---

## 0. Push to GitHub

```bash
cd dental
git init                       # if the repo isn't initialised yet
git add .
git commit -m "AI dental receptionist & patient automation platform"
git branch -M main
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main
```

Before pushing, confirm no secrets are staged:

```bash
git status --short             # .env / .env.local must NOT appear
git grep -nE "sk-|gsk_|AC[0-9a-f]{32}" -- . ':!*.md' || echo "no key-shaped strings found"
```

`.gitignore` already excludes `.env`, `.env.*` (except `.env.example`), `node_modules/`, `.next/`, `.venv/`
and `*.db`.

## 1. Backend → Render (blueprint included)

1. **New → Blueprint** and pick the repository. `render.yaml` creates the `brightsmile-api` web service and a
   free PostgreSQL database, wiring `DATABASE_URL` automatically.
2. Set these in the service's **Environment** tab:

   | Key | Value |
   |---|---|
   | `CORS_ORIGINS` | `https://<your-app>.vercel.app` |
   | `PUBLIC_SITE_URL` | `https://<your-app>.vercel.app` |
   | `DEMO_MODE` | `true` (recommended for a public portfolio demo) |
   | `ADMIN_API_KEY` | generated by the blueprint — copy it, the frontend needs the same value |
   | `GROQ_API_KEY` etc. | optional integration keys |

3. Deploy, then check `https://<service>.onrender.com/api/health`.

**Free-tier note:** Render's free web services sleep after inactivity, so the first request can take ~50
seconds. The frontend surfaces that as "The API server is offline" until it wakes. Either warm it with an
uptime pinger or use a paid instance for live demos.

### Backend → Railway (alternative)

1. **New Project → Deploy from GitHub repo.** `railway.json` builds `backend/Dockerfile`.
2. Add the **PostgreSQL** plugin — Railway injects `DATABASE_URL`.
3. Add `ADMIN_API_KEY`, `CORS_ORIGINS`, `PUBLIC_SITE_URL` (+ optional integration keys) as variables.
4. Generate a public domain; health check is `/api/health`.

### Backend → any Docker host

```bash
docker build -t brightsmile-api ./backend
docker run -p 8000:8000 --env-file backend/.env brightsmile-api
```

## 2. Frontend → Vercel

1. **Add New → Project**, import the repo, set **Root Directory** to `frontend`
   (framework preset: Next.js; build and install commands are auto-detected).
2. Environment variables:

   | Key | Value | Exposed to browser |
   |---|---|---|
   | `API_URL` | `https://<backend-url>` | no |
   | `ADMIN_API_KEY` | same value as the backend | no |
   | `ADMIN_PASSWORD` | optional — set it to lock `/admin` | no |
   | `ADMIN_SESSION_SECRET` | optional random string for the session cookie | no |
   | `NEXT_PUBLIC_SITE_URL` | `https://<your-app>.vercel.app` | yes |
   | `NEXT_PUBLIC_POSTHOG_KEY` / `_HOST` | optional analytics | yes |
   | `NEXT_PUBLIC_AGENCY_EMAIL` / `_CALENDAR_URL` | your contact details for `/solutions/dental` | yes |

3. Deploy, then go back and set the backend's `CORS_ORIGINS` / `PUBLIC_SITE_URL` to the Vercel URL.

## 3. Post-deploy checklist

- [ ] `GET /api/health` returns `{"status":"ok"}`
- [ ] The homepage chat answers a question (end-to-end through the proxy)
- [ ] `Run Demo` completes all 12 steps and books an appointment
- [ ] `/admin` loads and shows the seeded KPIs (1,284 / 247 / 86 / 42 / 31)
- [ ] `/admin/settings → API integrations` shows what you expect (demo vs connected)
- [ ] Browser devtools → the JS bundle contains **no** `ADMIN_API_KEY` or provider keys
- [ ] Mobile: the chat widget opens full screen and the dashboard is usable

## 4. Going live for a real practice

1. `DEMO_MODE=false` and set a strong `ADMIN_API_KEY` (the fallback demo key stops working).
2. Set `ADMIN_PASSWORD` so `/admin` requires a login.
3. Add the real integration keys (Groq/OpenAI, Twilio, Resend, Cal.com) — each falls back safely if missing.
4. Replace the fictional content: `backend/app/knowledge_base.py` (AI knowledge base + seed) and
   `frontend/src/lib/site.ts` (website copy), plus the images in `frontend/public/images/`.
5. Point `DATABASE_URL` at a managed PostgreSQL instance with automated backups.
6. Replace the in-process scheduler with a managed worker (Celery/RQ + Redis) and the in-memory rate limiter
   with a Redis-backed one before running more than one instance.
7. Complete a HIPAA review and sign business associate agreements with every vendor that will touch patient
   data. Until then, keep the demo banners in place.

## 5. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| "The BrightSmile API is offline" | Backend not running or `API_URL` wrong. Check `/api/health`. |
| `401 Admin login required` in the dashboard | `ADMIN_PASSWORD` is set but you're not signed in — go to `/admin/login`. |
| `401 Invalid or missing API key` from the backend | Frontend and backend `ADMIN_API_KEY` values differ. |
| Chat answers are generic | No LLM key, or the provider is unreachable (TLS/proxy). The receptionist falls back to knowledge-base answers by design; check the backend log for `LLM call failed`. |
| Emails/SMS never arrive | `DEMO_MODE=true` simulates them on purpose. Set it to `false` and add the keys. |
| CORS error in the browser | Add the exact frontend origin to `CORS_ORIGINS` (no trailing slash). |
| `Reset demo data` returns 403 | Only available while `DEMO_MODE=true`. |
| Slot booking returns 409 | The slot was taken between loading and booking — re-fetch availability. |
